# Latency metrics explained (p50, p90, p95)

This page explains **what** the summary numbers in the Call Traces UI mean, **how** we calculate them, and **what to tell customers**.

Related: [Call Traces overview](/docs/monitoring/call-traces/) · [Architecture](/docs/monitoring/call-traces/architecture/)

---

## 1. Why we measure latency

When someone talks to a voice AI agent, they notice **how long it takes to get a reply**.

- Too slow → the call feels broken or awkward.
- Fast and consistent → the call feels natural.

EfficientAI records each call as a **trace** and breaks it into **turns** (one back-and-forth: user speaks, agent replies).

We show two kinds of numbers:

| Kind | Plain English | Example labels in UI |
| --- | --- | --- |
| **Per-turn** | How long *this one* reply took | Turn table, waterfall bars |
| **Call summary** | How the *whole call* behaved on average and at the tail | **Response p50**, **p90**, **p95** in the header |

---

## 2. The three pipeline stages (Listen → Think → Speak)

Most voice agents run in three steps:

```
User speaks  →  [Listen]  →  [Think]  →  [Speak]  →  Agent audio plays
                 (STT)        (LLM)        (TTS)
```

| UI label | Technical name | What it measures |
| --- | --- | --- |
| **Listen** | STT (speech-to-text) | Time until we have the user's words |
| **Think** | LLM (language model) | Time until the model starts its answer |
| **Speak** | TTS (text-to-speech) | Time until the agent's voice starts playing |

Each stage has a **TTFB** value — **Time To First Byte** — in milliseconds:

- `stt_ttfb_ms` → Listen
- `llm_ttfb_ms` → Think
- `tts_ttfb_ms` → Speak

:::warning Not always additive
These three numbers are **not always additive**. The pipeline can overlap work (e.g. streaming). **Listen + Think + Speak ≠ Response latency** in general.
:::

---

## 3. Response latency

**Response latency** = *how long the caller waited for the agent to start responding* after they spoke.

In our data model this is `sut_response_latency_ms` (**SUT** = system under test, i.e. your voice agent).

### Where it comes from (best → fallback)

| Priority | Source | Meaning |
| --- | --- | --- |
| 1 (best) | Pipecat `turn.user_bot_latency_seconds` on the `turn` span | Measured end-to-end by the voice framework |
| 2 | Sum of Listen + Think + Speak when all three exist and user spoke | Derived estimate |
| 3 | Think (LLM) only | Partial fallback when other data is missing |

We **prefer measured end-to-end** over adding components.

### What you see in the UI

| UI label | Field | What it is |
| --- | --- | --- |
| **Response p50** | `response_latency_p50_ms` | Typical reply time for this call |
| **Response p90** | `response_latency_p90_ms` | 9 out of 10 turns were this fast or faster |
| **Response p95** | `response_latency_p95_ms` | 19 out of 20 turns were this fast or faster |
| **"13 of 14 turns"** | `response_latency_sample_count` | How many turns were used in the math (see [eligible turns](#6-which-turns-count)) |

Stage headers (Listen / Think / Speak p50) use the same percentile math but only on that stage's TTFB values.

## 4. Percentiles explained simply

### Average vs median

| Stat | Plain analogy | Problem |
| --- | --- | --- |
| **Average** | Add all wait times and divide | One very slow turn pulls the average up |
| **Median (p50)** | Sort all waits; pick the middle one | Better "typical" number |
| **p90 / p95** | How bad was it for the slowest 10% / 5%? | Shows tail pain |

| Label | Also called | Plain English |
| --- | --- | --- |
| **p50** | Median | Half the turns were **this fast or faster** |
| **p90** | 90th percentile | 90% of turns were **this fast or faster** |
| **p95** | 95th percentile | 95% of turns were **this fast or faster** |

**Example — 10 turns** (response times in ms):

```
[600, 700, 750, 800, 850, 900, 950, 1100, 1500, 3000]
```

- **p50 ≈ 875 ms** — a typical turn
- **p90 ≈ 1500 ms** — most turns were under ~1.5 s
- **p95 ≈ 3000 ms** — the very slowest turns

## 5. The formula

We use the **nearest-rank** method.

### Steps

1. Collect one response latency per **eligible** turn ([section 6](#6-which-turns-count)).
2. Sort the list **smallest → largest**.
3. Pick the index:

```
n = number of values
idx = min(n − 1, round((percent / 100) × (n − 1)))
answer = sorted_values[idx]
```

4. Round to **one decimal place** (e.g. `1100.0` ms).

We do **not** interpolate between two values — we pick an actual turn from the sorted list.

### Worked examples

#### What does the number we multiply by mean?

**It is not "number of turns minus one excluded."** It is the **last array index** when positions start at 0.

| Symbol | Meaning |
| --- | --- |
| **n** | How many latency values are in the sorted list (after eligibility) |
| **n − 1** | The index of the **last** value (arrays count from 0, not 1) |
| **idx** | Which slot we pick in the sorted list (0 = smallest, n−1 = largest) |

**Example A uses all 4 turns** — nothing is dropped in this step. Turn exclusion (e.g. "13 of 14 turns") happens **earlier**, when we build the list.

#### Example A — 4 values: `[800, 920, 1100, 1400]`

Here **n = 4**, so we multiply by **n − 1 = 3** (the last index is 3, not 4):

| Index (idx) | 0 | 1 | 2 | 3 |
| --- | --- | --- | --- | --- |
| Value (ms) | 800 | 920 | 1100 | 1400 |
| Human label | 1st | 2nd | 3rd | 4th |

| Percentile | Calculation | idx picks | Result |
| --- | --- | --- | --- |
| p50 | round(0.5 × **3**) = **2** | 3rd value | **1100 ms** |
| p90 | round(0.9 × **3**) = **3** | 4th value | **1400 ms** |
| p95 | round(0.95 × **3**) = **3** | 4th value | **1400 ms** |

With only 4 samples, p90 and p95 both land on the slowest turn.

#### Example B — 3 values: `[1200, 2400, 3600]`

Here **n = 3**, multiply by **n − 1 = 2**:

| Percentile | Calculation | Result |
| --- | --- | --- |
| p50 | round(0.5 × **2**) = 1 → 2nd value | **2400 ms** |
| p90 | round(0.9 × **2**) = 2 → 3rd value | **3600 ms** |

#### Example C — 1 value: `[850]`

**n − 1 = 0**. Every percentile uses index 0 → **850 ms**.

#### Quick reference

| Values in list (n) | Multiply by (n − 1) | Last index |
| --- | --- | --- |
| 4 | **3** | 3 |
| 10 | **9** | 9 |
| 13 | **12** | 12 |
| 14 eligible turns | **13** | 13 |

## 6. Which turns count

Not every row in the turn table is included. We only want turns that represent a **real user → agent exchange**.

**Included**

| Situation | Counts? |
| --- | --- |
| User spoke and agent replied | **Yes** |
| Agent greeting with measured end-to-end latency | **Yes** |
| Speech-to-speech (S2S) with measured latency | **Yes** |

**Excluded**

| Situation | Why |
| --- | --- |
| Agent-only opener with no user speech and only LLM timing | Not a real "user waited for reply" sample |
| Turn with only partial LLM fallback | Incomplete measurement |
| Turn with no response latency | Nothing to measure |

That's why you may see **"13 of 14 turns"** — 14 turns exist, but only 13 were valid samples.

## 7. Turn states

| Badge | Meaning | Affects percentiles? |
| --- | --- | --- |
| **Incomplete** | Missing STT, LLM, or TTS data | Usually excluded |
| **Interrupted** | Turn cut short | Included if measured |
| **Talk-over** | User spoke over agent | Included if measured |
| **Opener** (Turn 1) | Bot greeting | Often excluded unless end-to-end measured |

**Turn numbering:** Pipecat Turn 1 is often the **greeting window**. The first real user message may show as Turn 2. This is expected.

## 8. Per-turn vs call summary

| Question | Look at |
| --- | --- |
| How long did Turn 5 take? | That turn's **Response** column |
| Was this call generally fast? | Header **Response p50** |
| Did we have bad spikes? | **p90 / p95** |
| How fast is our STT? | **Listen p50** |

**Waterfall bar length** = span duration on the timeline. **Table TTFB** = time to first byte. Use TTFB for latency SLOs.

## 10. Customer FAQ

**Q: What is p50?**  
A: The middle reply time — half the turns were faster, half were slower.

**Q: Why not use average?**  
A: One very slow turn skews an average. Percentiles show typical (p50) and tail (p95) more honestly.

**Q: Why does p50 not equal Listen + Think + Speak?**  
A: Response latency is measured end-to-end. Stages can overlap — we measure what the caller experienced.

**Q: Why "13 of 14 turns"?**  
A: We only include turns where the user spoke and we have a trustworthy measurement.

**Q: Is this the same as phone provider latency?**  
A: Not always. We measure your **AI pipeline**. Telephony adds delay that may not appear in OTLP traces.

**Q: Can I use this for billing?**  
A: p50 / p95 are for **quality monitoring**. Billing uses separate cost fields.

## 11. Quick reference

```
CALL HEADER
  Response p50 / p90 / p95  ← sut_response_latency_ms per eligible turn
  "N of M turns"            ← eligible sample count

STAGE ROWS
  Listen p50  ← stt_ttfb_ms
  Think p50   ← llm_ttfb_ms
  Speak p50   ← tts_ttfb_ms

FORMULA
  sort → idx = round(pct/100 × (n−1)) → pick value → round to 0.1 ms
```
